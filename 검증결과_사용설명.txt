차곡 · 단일 HTML 영수증 가계부
검증일: 2026-11-07 / Windows / 설치된 Google Chrome / file:// 직접 실행

1. 실행 방법

영수증_가계부.html을 Chrome에서 엽니다. 최종 HTML은 약 35.9MB이며 모델과 실행기가 모두 들어 있습니다.
별도 설치, 서버 실행, 회원가입, 첫 실행 시 모델 다운로드가 필요하지 않습니다.
개발용 receipt-work 폴더는 실행에 필요하지 않습니다. HTML 하나만 다른 폴더로 복사해도 실행할 수 있습니다.
Edge 등 다른 최신 WASM SIMD 지원 브라우저에서도 실행하도록 구성했지만 실제 자동 검증은 Chrome에서 했습니다.

이미지 파일 선택 또는 드래그 앤 드롭 → 전체 분석 → 원본·보정 이미지와 추출값 대조 → 빈칸 입력 → 저장/CSV 다운로드 순으로 사용하세요.
처음 분석할 때만 HTML 내부 바이트로 모델을 초기화합니다. 해당 PC에서는 합성 이미지 첫 분석 약 2.1초, 후속 약 0.4~0.6초였으며 사진·PC 성능에 따라 달라집니다.
밝기·대비·기울기와 90도 회전은 원본 파일을 바꾸지 않습니다. 보정 변경 이후 OCR 결과는 재분석 전까지 이전 이미지 기준입니다.
원본 이미지는 편집 화면의 '원본 이미지 펼치기'에서 별도로 확인할 수 있습니다.

2. 단일 HTML / PaddleOCR 가능성 선행 검증

결론: 이 환경에서 가능함을 실제 실행으로 확인했습니다. Python PaddleOCR 실행기를 HTML에 넣은 것은 아닙니다.
PaddleOCR 검출·한국어 인식 모델의 ONNX 변환본을 ONNX Runtime Web의 WASM 실행기로 직접 추론합니다.
공식 PaddleOCR.js SDK를 그대로 포함하지 않고 전처리, 검출 후처리, 한국어 CTC 디코딩을 앱 코드에 구현했습니다.
브라우저에서 검출 모델 입력 이름 x, 인식 모델 입력 이름 x를 확인하고 실제 이미지 추론을 실행했습니다.

최종 구성:
- PaddleOCR PP-OCRv3 검출 ONNX: 2,429,873 bytes
- PaddleOCR korean PP-OCRv5 인식 ONNX: 13,401,252 bytes
- 해당 v5 한국어 문자 사전: 47,451 bytes, blank/space 포함 디코더 11,947개 항목
- ONNX Runtime Web 1.17.3 JS: 542,655 bytes
- 같은 버전 SIMD WASM: 10,551,547 bytes
- 모두 Base64/인라인 JS로 HTML 안에 포함

단일 스레드 WASM을 선택하여 COOP/COEP 응답 헤더, 서버, SharedArrayBuffer 의존성을 피했습니다.
WASM은 내장 바이트에서 Blob URL로 만들고, 모델은 Uint8Array로 세션에 전달합니다.
런타임 설치나 외부 CDN 접속으로 대체하지 않았습니다. 다른 OCR 엔진으로 임의 교체하지 않았습니다.
Tesseract 등의 대체 엔진은 최종 결과물에 사용하지 않았습니다. PaddleOCR 경로가 실제 실행되므로 대체 승인도 필요하지 않았습니다.

ONNX 파일은 아래 공개 변환 미러에서 받았습니다. 원본 Paddle 가중치와 바이트 단위 동등성을 독립 검증한 것은 아닙니다.
v3 검출과 v5 인식을 각기 정규화해 연결한 사용자 정의 파이프라인이며 공식 전체 SDK와 동일한 정확도를 보장하지 않습니다.

3. 정확도 개선 과정과 반복 검증

초기: PP-OCRv3 한국어 모델 + 검출을 단일 HTML에 넣고 네트워크를 차단한 상태에서 공개 한국어 영수증 2장을 추론했습니다.
문제: 첫 스캔 영수증의 한글·금액이 다수 깨졌습니다.
변경: 한국어 PP-OCRv5 모델 및 일치하는 사전으로 교체했습니다.
같은 초기 검출 설정에서 평균 모델 신뢰도는 첫 표본 0.533→0.719, 둘째 0.807→0.930으로 변화했습니다.
이 수치는 모델의 신뢰도이며 정답률이나 실제 정확도가 아닙니다.

추가 수정:
- 검출 영역의 여백을 늘려 잘린 획을 줄임
- 낮은 신뢰도 영역은 흑백 대비 보정 후 재인식하고 더 높은 신뢰도를 선택
- 인식기가 지운 열 사이 공백은 이미지의 흰 세로 간격과 CTC 문자 위치를 함께 사용해 복원
- 인식 문자열의 글자 자체가 바뀌지 않는 경우에만 공백 복원 적용
- 숫자 열을 임의 길이로 분할하거나 수량·단가를 추측하지 않음
- 영수증의 기울어진 같은 행을 위치로 묶음
- 품명이 앞줄에 있고 바코드·단가·수량·금액이 다음 줄인 배치를 지원
- 합계보다 명시적인 결제금액을 우선하고 승인금액·발급사 연결을 제한적으로 지원

검증 이미지들은 공개 저장소에서 검증용으로 내려받았습니다. 최종 HTML에 포함하지 않았으며 별도 재배포용 이미지 묶음을 만들지 않았습니다.

4. 정상 5개 OCR 시나리오

요청문에 개별 테스트의 구체 입력·정답이 따로 없으므로 아래 대표 입력을 명시하여 검증했습니다.
알려진 문자열을 Windows 한글 글꼴로 Canvas에 그린 합성 이미지입니다. 실제 사진 표본과 별도입니다.

정상1: 사과 1000 × 2, 합계/현금 2000
결과: 날짜, 품목 1개, 결제 1개, 총금액 2000 일치

정상2: 사과 1000 × 2 + 우유 3000 × 1, 합계/현금 5000
결과: 품목 2개, 결제 1개, 총금액 5000 일치

정상3: 사과 금액 2000, 품목 할인 100, 추가 할인 50, 합계/현금 1850
결과: 품목 할인 100과 별도 할인 50 분리, 품목 1개, 총금액 1850 일치
할인 전·후 기준이 원문에 없으면 그 기준은 빈칸입니다. 사용자가 할인 전을 선택하면 계산 합계 1850으로 확인합니다.

정상4: 사과 금액 2000, 현금 500 + 신용카드 1500
결과: 품목 1개, 결제 2개, 총금액 2000 일치. 품목 CSV 행이 결제 수만큼 늘어나지 않음

정상5: 정상1 이미지를 90도 회전해 입력, 앱의 270도 보정으로 복구
결과: 날짜, 품목 1개, 결제 1개, 총금액 2000 일치

다섯 합성 이미지의 공백을 제외한 문자 편집오류율(CER)은 모두 0이었습니다.
적은 수의 또렷한 합성 샘플 결과이며 일반 영수증 정확도 100%를 뜻하지 않습니다.

5. 잘못된 입력 5개 및 내장 자체 테스트

오류1: 2026-02-30, 2026-13-01 → 실제 날짜 검증 실패
오류2: -1, abc, 입력란의 1,000 → 숫자 형식 오류 (입력은 쉼표 없는 원 단위 정수)
오류3: 수량 0, -2 → 오류
오류4: 인쇄 금액 1000, 할인 100, 할인 전·후 미지정 → 할인 반영 계산값 미확정
오류5: 카드 1234-5678-9012-3456, 손상 PNG 바이트 → 번호 마스킹 / 이미지 시그니처 거부

앱 맨 아래 '내장 자체 점검'에서 정상 5개 규칙과 오류 5개 규칙을 다시 실행할 수 있습니다.
정상 규칙 테스트: 윤년, 0과 빈칸 구분, 품목/전체 할인 계산, 할인 후 금액 중복 차감 방지, CSV BOM/따옴표/수식 방어.
내장 10개 모두 PASS.

6. 브라우저 기능 검증

최종 HTML을 file://로 열고 Playwright 브라우저 컨텍스트를 offline으로 전환한 상태에서 실행했습니다.
테스트 스크립트는 개발 검증 전용이며 사용자가 HTML을 실행하는 데 필요하지 않습니다.

다음 13개 시나리오 모두 PASS:
1) 내장 정상5/오류5
2) 다중 파일, 동일 내용 해시 중복, 손상 파일 안내
3) 원문 파싱, 복수 결제, 할인 분리, 품목 CSV 행 중복 방지
4) 품목 없는 영수증 한 행, 공통 금액 중복합산 경고
5) IndexedDB 저장 → 페이지 재로드 → 수동 복원
6) 날짜 오류, 사용자 수정 출처
7) 오프라인 CSV 실제 다운로드, 첫 3바이트 EF BB BF 확인
8) 재분석 덮어쓰기 확인에서 취소 시 사용자 수정값 유지
9) 1440px / 390px 화면, 페이지 가로 넘침 없음
10) JPG 업로드 및 WEBP 실제 DragEvent 끌어다 놓기 (PNG/JPEG는 실제 표본으로 확인)
11) QuotaExceededError 주입 시 저장 공간 부족 안내, 이전 저장본 유지
12) 전체 삭제 확인에서 취소 시 데이터 유지
13) 외부 HTTP/HTTPS 요청 0건, 페이지 런타임 오류 0건

추가 OCR 일괄 테스트: 테스트 메모리에 손상 이미지 1개를 넣고 유효 영수증을 뒤에 배치했습니다.
결과: 첫 파일은 실패 이유 표시, 뒤 파일은 59개 OCR 영역을 처리하며 계속 진행.
공개 영수증 OCR 결과도 오프라인 저장·재로드·복원했습니다.

7. 직접 재현할 테스트 순서

1) HTML을 복사해 새 폴더에 놓고, 인터넷 연결을 끊은 뒤 Chrome에서 엽니다.
2) 영수증 JPG/PNG 등 2개를 선택하고 하나를 다시 넣어 중복 경고를 확인합니다.
3) 텍스트 파일의 확장자를 png로 바꾼 파일을 넣어 손상/형식 안내를 확인합니다.
4) 전체 분석 후 파일 목록 상태, 진행률, OCR 원문·위치·신뢰도를 확인합니다.
5) 회전·기울기·밝기·대비를 바꾼 뒤 원본이 유지되는지 보고 재분석합니다.
6) 품목·결제 행을 추가/삭제하고 각 입력값을 바꿉니다. 빈칸과 0의 차이를 확인합니다.
7) 품목 금액 1000, 할인 100을 넣습니다. 할인 전이면 900, 할인 후이면 1000이며 미지정이면 미확정이어야 합니다.
8) 별도 할인 50을 넣고 최종금액·결제합계와의 차액 경고를 확인합니다.
9) 날짜 2026-02-30, 금액 -1, 수량 0을 각각 넣고 오류를 확인합니다.
10) 수정한 뒤 재분석을 눌러 덮어쓰기 확인을 취소하고 수정값 유지 여부를 확인합니다.
11) 브라우저에 저장 → 창을 닫고 같은 경로의 HTML 다시 열기 → 저장본 복원을 누릅니다.
12) 품목/영수증요약/결제상세 CSV를 각각 다운로드하고, 품목 한 행 원칙과 UTF-8 한글을 확인합니다.
13) 상호에 =1+1 또는 @SUM(1)을 입력한 뒤 CSV에서 앞에 작은따옴표가 붙는지 확인합니다.
14) 마지막에 자체 점검 10개를 실행합니다. 전체 삭제는 확인 대화상자를 읽고 선택합니다.

저장본은 HTML에 다시 써 넣는 방식이 아닙니다. 이 브라우저 프로필과 파일 위치/출처의 IndexedDB에 있습니다.
HTML을 옮길 때 브라우저 저장본이 따라간다고 가정하면 안 됩니다. 데이터 이동용 전체 백업/복원 기능은 이번 범위에 넣지 않았습니다.
CSV는 데이터 내보내기이며 원본 이미지/보정 설정/OCR 전체를 복원하는 백업 형식이 아닙니다.

8. 계산·저장·개인정보 정책

- 모든 이미지 디코딩·보정·OCR·파싱·계산·CSV 생성을 브라우저에서 처리합니다.
- CSP로 외부 스크립트, 이미지 URL, 폼 전송, 외부 연결을 막습니다. 네트워크 연결 정책은 connect-src blob:만 허용합니다.
- 원본·OCR·추출값을 보내는 API, 분석 도구, 외부 폰트가 없습니다.
- 모델 미러 다운로드는 제작 단계에서만 수행했습니다. 사용자 영수증을 다운로드 서버에 보내지 않았습니다.
- 카드번호로 의심되는 13~19자리 긴 숫자를 OCR·근거 텍스트에서 마스킹합니다. 원본 이미지의 카드번호 자체는 원본 보존 요구에 따라 남아 있습니다.
- 번호 마스킹은 보수적이어서 바코드나 여러 숫자 열이 이어진 근거 문장도 가릴 수 있습니다. 이 경우 원본 이미지와 영역별 OCR을 대조하세요.
- 결제 끝 4자리 입력란은 숫자 네 자리만 저장합니다. 원본에서 뒤 네 자리가 가려진 경우 추측하지 않습니다.
- 각 영수증·품목·결제는 UUID와 receiptId로 연결됩니다.
- 모든 금액 입력은 쉼표 없는 음수가 아닌 정수이며, 수량은 0보다 큰 숫자입니다. 빈칸과 0은 구분됩니다.
- 할인 없음이 확인되면 0을 직접 입력합니다. 빈 할인을 자동 0으로 바꾸지 않습니다.
- 품목 금액이 할인 후라면 품목 할인을 다시 차감하지 않습니다. 별도 할인은 영수증당 한 번만 차감합니다.
- 같은 전체 할인과 품목 할인의 관계가 불명확하면 자동 연결하지 않고 사람이 확인하도록 남깁니다.
- 저장 실패는 기존 IndexedDB 저장본을 덮어쓰지 않습니다. 비공개 모드·브라우저 데이터 삭제·저장소 정책에 따라 데이터가 사라질 수 있습니다.
- CSV는 UTF-8 BOM, 큰따옴표 이스케이프, CRLF, 수식 시작 문자 앞 작은따옴표를 사용합니다.
- CSV 날짜는 검증된 YYYY-MM-DD, 금액은 원 기호와 천 단위 구분자 없는 숫자입니다. 잘못된 값은 빈칸으로 내보내고 경고 열에 오류를 유지합니다.
- 품목 CSV의 공통금액은 행마다 반복되므로 합산하지 마세요. 영수증 요약 CSV는 영수증당 한 행입니다.

9. 남은 한계

일반 영수증의 완전 자동 추출 정확도를 보장하지 않습니다. 실제 표본에서 품목 누락과 상호·품명 오인식이 확인되었습니다.
결제정보의 연관관계가 불명확하거나 낮은 신뢰도인 값은 추측하지 않고 수동 입력을 요구합니다.
검출 좌표는 글자 한 자씩의 정밀 경계가 아니라 텍스트 영역의 축에 평행한 사각형입니다. 보정 이미지 픽셀 기준입니다.
기울기·회전은 수동 보정입니다. 자동 원근·접힘·곡면 보정, 학습 기반 표 구조 복원은 없습니다.
파일당 20MB, 이미지 3,200만 화소, 한 번에 최대 100장, 이미지당 검출 영역 350개로 제한했습니다.
SIMD 미지원 브라우저, 스마트폰 로컬 파일 실행, Safari/Firefox는 검증하지 않았습니다.
원화 구매 영수증만 대상으로 하며 PDF, 외화, 반품, 통계, 회원가입, 클라우드, 외부 연동은 제외했습니다.
